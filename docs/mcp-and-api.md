# What the API and MCP server can do

The product is **a4a** (agenda): a YouTrack-style tracker of issues, boards and plans, in the family of a7c (autonomic), a5s (agentos) and a3t (ambit).

This document is the capability design for the two programmatic surfaces:

- the **REST API**, for scripts, integrations and the web UI itself, and
- the **MCP server**, for AI agents (Claude Code, Claude Desktop, Cursor, custom agents).

Items marked **(later)** are deliberately out of v1 and listed under [Open questions](#9-open-questions).

---

## 1. Who talks to a4a

| Client | Surface | Typical jobs |
|---|---|---|
| People in the browser | Web UI → REST API | Everything. The UI has no private endpoints. |
| Scripts and integrations | REST API + webhooks | CI files a bug when a build breaks; GitHub, GitLab, Bitbucket, Gitea or Forgejo links commits and pull requests, and `PROJ-12 #Fixed` resolves an issue; importers; dashboards and reports |
| Coding agents (Claude Code, Cursor) | MCP | Pick up an issue, move it to *In Progress*, comment progress, link follow-ups, resolve it when done |
| Assistant agents (Claude Desktop, custom) | MCP | Triage the backlog, write status reports and release notes, find duplicates, plan sprints |
| Event-driven agents | Webhooks / SSE + MCP or REST | React when something happens: triage new issues, notify on blockers |
| Agents with a person's token | MCP `list_notifications` | See what's waiting for their person: assigned, mentioned, changes on what they watch |
| People outside the team | The help desk's public pages, email and portal (no team account) | Ask a project for help, follow the request, answer the team's replies |
| Guests (no sign-in) | REST's reading routes and the web's public pages | Read a project an administrator opened to anyone: its issues, articles, boards, reports, plan and whiteboards (D37, D64) |
| Project managers (waterfall or hybrid) | Web UI + REST + MCP | Gantt timeline with critical path, resource levelling, cost tracking against a budget, baselines and earned value |
| The built-in AI assistant | Same tool layer as MCP | Chat with your projects; it asks before it changes anything, unless you let it act |

## 2. Design principles

1. **API-first.** Anything you can do in the UI you can do over REST. An OpenAPI 3.1 spec is served at `/api/v1/openapi.json`, with interactive docs at `/api/docs`.
2. **MCP is curated for agents, not a mirror of REST.** 60 task-shaped tools (5.1) instead of some 440 endpoints. They take readable IDs (`PROJ-12`) and names (`"Priority": "Critical"`), not internal IDs. Output is compact and agent-readable. Errors tell the agent how to fix the call (for example *"Unknown value 'Fixd' for State. Did you mean 'Fixed'?"*).
3. **One tool layer, three surfaces.** The MCP tools and the in-app assistant's tools are the same code, running over the same services as REST, with the same validation and permission checks.
4. **One permission model.** Every API token belongs to a user and acts as that user. Token scopes (`read`, `write`, `admin`) can only narrow what the user may do, and a token can be limited to some projects.
   - Each project is open, or members only. In a project a person is a viewer (reads, comments), a member (also changes issues) or a manager (also its settings, people, boards and baselines); its lead and administrators are managers.
   - What you can't see answers exactly as what doesn't exist (404), on every surface: REST, MCP, search, links, events, SSE and AI.
5. **Safe by default for agents.**
   - MCP cannot delete issues.
   - Commands support `dry_run`.
   - Bulk commands are capped at 50 issues per call.
   - Every tool carries MCP annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`), so a client can auto-approve reads and ask before writes.
   - The in-app assistant asks the user before every write, unless they let it act (`approvalMode: "auto"`).
6. **Everything is attributed.** The activity log records who made each change and through which channel, plus the token or integration name. The channels are `web`, `api`, `mcp`, `assistant`, `automation`, `system`, `helpdesk` (people outside the team, through the help desk), `vcs` (a commit or pull request, through an integration), `chat` (Teams or Slack), `ci` (a build), `email` (the team answering a notification email) and `app` (an app, D48). History names the token and whom it acted for: *"claude-code, over MCP, for Anna Schmidt"* changed *State: Open → In Progress*. A change a workflow rule made says which rule, in its `data.automation`.
7. **Built for retries and concurrent editors.**
   - Any `POST` accepts an `Idempotency-Key` header, so a retried request doesn't create a second issue.
   - Issue updates accept `expectedVersion` and return `409 Conflict` when someone else changed the issue first, so an agent can't silently overwrite a human's edit.

## 3. Two small languages shared by every surface

The YouTrack-style **query language** and **command language** are the backbone. The UI search bar, `GET /issues?query=`, the MCP `search_issues` and `apply_command` tools, and the AI features all use them.

**Search queries**

```text
project: BACK #Unresolved Priority: Critical, Major for: me sort by: updated desc
Type: Bug created: -7d .. today -State: Duplicate "login page"
depends on: BACK-12 or subtask of: BACK-3
has: -Assignee tag: regression
watcher: me #Unresolved sort by: updated desc
has: request sla: overdue
```

- Fields are referenced by name, and multi-word values work without quotes (`State: In Progress`).
- Supported: ranges (`a .. b`, `*`), negation (`-value`), `and` / `or` / parentheses, and relative dates (`today`, `{this week}`, `-14d`, and `Overdue`, any day before today). Dates are read in the asker's time zone (their profile's, or the server's), and a day of `created`, `updated` or `resolved` runs from their midnight to their next; a query's explanation names the zone when its dates depend on it. Workflow rules read them in the server's.
- Free text is searched across summaries, descriptions and comments.
- `sort by:` accepts several keys.

**Commands** (applied to one or more issues)

```text
State Fixed Assignee john tag regression
Critical In Progress            # field names can be omitted when the value is unambiguous
subtask of BACK-3 Estimation 2d
remove tag needs-info duplicates BACK-7
sprint Sprint 4                 # into a sprint of a board of the issue's project; "remove sprint Sprint 4" takes it out
```

- Every command can be **previewed** (`dryRun`), which returns the exact field changes per issue without applying them.
- A command can carry a comment, which is posted together with the changes.

## 4. REST API (v1)

**Base path:** `/api/v1`

**Authentication**

- Session cookie for the web UI.
- `Authorization: Bearer a4a_…` for API tokens.
- Nothing, for a guest: where an administrator opened a project to anyone, a request without credentials to a reading route (projects, issues and their comments, links, history and files, search, articles, fields, tags and link types; and boards, reports, plans and whiteboards, D64) reads those projects, and nothing else; `GET /guest` lists them (D37). Those routes say so in OpenAPI: their security has an empty requirement beside the token and the cookie.

**Conventions**

- **Errors:** `{ "error": { "code", "message", "hint?", "details?", "key?", "values?" } }`. `message` and `hint` are English, for programs and agents; `key` and `values`, where a problem has them, say the same problem for a page in another language: `problem.<key>` in the catalogs (D49). A list among the values comes as a list, for the page to join in its own language: an array of words, which `message` and `hint` join with ", " (`"names": ["Priority", "State"]`), or `{ "and": [...] }` and `{ "or": [...] }`, which they join with "and" or "or".
- **Language:** the API and MCP speak English. A page says its language in `x-a4a-locale`, which the server uses for the inbox's titles it answers and the problems' keys; emails and push are in each recipient's language (their profile's, else `DEFAULT_LOCALE`; a help desk requester's choice on the portal, else their browser's there, else `DEFAULT_LOCALE`, D63's revisit).
- **Lists:** paginated as `?offset=&limit=` → `{ total, items }`.
- **IDs:** readable issue IDs are accepted everywhere.
- **Custom fields:** set by name, as `{"fields": {"Priority": "Critical", "Assignee": "anna"}}`.

**Example: what scripts can do with it**

- **CI bot**
  1. On a red build it sends `POST /issues` with `Idempotency-Key: build-4711`, `Type: Bug` and `tag: ci-failure`, so a retry never duplicates the issue.
  2. When the build goes green again it sends `POST /commands` with `State Fixed`.
- **CI builds.** Built in: a build source takes GitHub Actions' runs, or Forgejo's and Gitea's, or a step posts `POST /builds/hooks/{id}` with the build and its commits (README, Builds from CI); the resolved issues they name get the build in Fixed in build.
- **Commit hook.** Built in: add a version control integration (GitHub, GitLab, Bitbucket, Gitea or Forgejo), and a commit message like `BACK-12 #Fixed` links the commit and applies the command as its author. Without one, a hook can send `POST /commands {issues:["BACK-12"], command:"State Fixed", comment:"Fixed in a1b2c3"}`.
- **Weekly report.** `POST /search/count {query:"project: BACK #Unresolved", groupBy:"Priority"}`.
- **Chat bot.** Built in for Teams and Slack (D42): a channel subscribed to a project hears of its issues, and people ask the bot as themselves. For another chat, read `GET /events/stream` and post "BACK-12 moved to In Progress by anna".
- **Stand-up bot.** `GET /reports/burndown?board=Backend sprints` says how the sprint stands, in a sentence: "Behind: 26h left, where the ideal had 20h left as today began".
- **Timesheets.** `GET /reports/time.csv?rows=entries&from=2026-11-01&to=2026-11-30` for the month's entries, as a spreadsheet opens them.
- **Moving from Jira.** `POST /imports?project=WEB` with the export, then `PUT /imports/{id}/mapping` for what wasn't found, `POST /imports/{id}/check`, and `POST /imports/{id}/run`; follow it with `GET /imports/{id}`.
- **Moving from YouTrack, without an export.** `POST /imports/from-api` with `{"project": "WEB", "source": "youtrack", "url": "https://example.youtrack.cloud", "query": "project: WEB", "credentials": {"token": "perm:…"}}`. Follow `GET /imports/{id}` until it is `ready`, then map, check and run as above, giving the same `credentials` to `run` when it brings files. A Jira Cloud token goes with its account's `email`; a Jira Data Center personal access token goes alone. Not over MCP: an agent would pass the other tracker's token through a model's context.

### 4.1 SCIM 2.0 (provisioning)

`/scim/v2`, for an identity provider (D38), with `Authorization: Bearer a4s_…` (a SCIM token, from Administration → Provisioning) and `application/scim+json`.

- `GET/POST /Users`, `GET/PUT/PATCH/DELETE /Users/{id}`; `GET/POST /Groups`, `GET/PUT/PATCH/DELETE /Groups/{id}`; `GET /ServiceProviderConfig`, `/ResourceTypes`, `/Schemas`.
- Filters: `attribute eq "value"`, on `userName`, `externalId`, `emails.value` or `displayName` (users) and `displayName`, `externalId` (groups). Paging by `startIndex` and `count` (200 at most). `excludedAttributes=members`.
- PATCH takes `add`, `replace` and `remove` in any case, `"True"`/`"False"`, filtered paths such as `emails[type eq "work"].value` and `members[value eq "…"]`, and a value with no path. Unknown attributes are let be.
- Deactivating (`active: false`) or deleting bans; the account and its history stay. Groups follow the provider. A PATCH to a group answers 204.
- Errors are SCIM's: `{ "schemas": ["urn:ietf:params:scim:api:messages:2.0:Error"], "status", "scimType?", "detail" }`, the detail saying what to change.

## 5. MCP server

**Transport and auth**

- **Endpoint:** `POST /mcp` on the same server, using Streamable HTTP (stateless) with `Authorization: Bearer …`. The tool calls act as the token's user.
- **Signing in (OAuth 2.1, docs/architecture.md D28):** a client that signs in by itself needs only the address. Without a token, `/mcp` answers 401 with `WWW-Authenticate: Bearer realm="a4a", resource_metadata="<PUBLIC_URL>/.well-known/oauth-protected-resource/mcp", scope="read write"`, and the client goes from there (5.6). Its access token (`a4o_…`) works at `/mcp` alone.
- **API tokens** (`a4a_…`) work too, for clients that don't sign in by themselves.
- **stdio:** for clients that only speak stdio, the `a4a-mcp` bridge connects stdio to `/mcp` using `A4A_URL` + `A4A_TOKEN`.

Every tool and resource sees only what its token's person may see, in the projects the token reaches: a hidden project or issue is "not found", exactly as a missing one.

Deliberately **not** exposed over MCP in v1: deleting issues, articles, files or whiteboards (D58: a whiteboard holds a team's work, and removing a card or a note stays undoable while a whole whiteboard isn't), user and permission admin (changing a project's people included), webhooks, settings, integrations, imports, a help desk's settings, how people and requesters sign in (D62, D63, D69), email and push preferences (they're the person's own, in the web app), undoing an agent's change (a person decides that, D34), a view's `view` and its undo (agents don't make view edits: what an agent changes is an agent's change, D34's revisit), writing help (an agent is a model, and writes its own words, D59), and making or changing workflow rules. A rule acts later, on its own, on every issue that ever matches it, outliving the conversation and the caps on a command (50 issues, a dry run first); and an agent reads issue text, which anyone can write. So agents can list rules and preview one (`preview_rule`), and a person makes it, on the Rules page or over REST.

`get_issue` says when an issue is a help desk request (who asked, and the language a4a writes to them in when it knows one, `requester.language`, so an agent can answer in it; whether by the form or by email, its first-response target, who is copied on it, its customer group, and whether it's kept from the group) and which comments are public, so an agent knows what the requester has seen. Making and changing customer groups is a desk's setting, and stays off MCP with its others.

**Why agents may attach files, and only small ones.** Agents produce things worth keeping beside an issue: a log excerpt, a failing test's output, a patch, a script that reproduces a bug. So `attach_file` exists, through the same service as every upload: the type is read from the bytes, the per-issue cap applies, the file is served as a download, and its activity names the token. But a file over MCP is base64 or text inside a tool call, so every byte passes through the model's context: 256 KB is about what an agent can sensibly write out. A larger file goes to `POST /issues/{id}/attachments` with the same token.

### 5.6 Signing in with OAuth

a4a is the authorization server for its own `/mcp`, following MCP's authorization specification. Every address below is `PUBLIC_URL`'s. They answer only when `PUBLIC_URL` is https (or this computer) and `MCP_OAUTH` isn't `false`; otherwise the metadata is 404 and `/mcp` asks for a token as before. The protocol's endpoints answer any origin, without credentials; nothing else does.

| Endpoint | What it is |
|---|---|
| `GET /.well-known/oauth-protected-resource/mcp` (and `/.well-known/oauth-protected-resource`) | RFC 9728: `resource` is `PUBLIC_URL/mcp`, its authorization server is `PUBLIC_URL`, its scopes `read` and `write` |
| `GET /.well-known/oauth-authorization-server` | RFC 8414: the endpoints below; `response_types` `code`; grants `authorization_code` and `refresh_token`; PKCE `S256`; client authentication `none`; `iss` in the answer (RFC 9207) |
| `POST /oauth/register` | RFC 7591, JSON. Public clients only: `client_id`, never a secret. `redirect_uris` are https, or http to `127.0.0.1`, `[::1]` or `localhost`. 20 an hour per address. Or no registration at all: below |
| `GET /oauth/authorize` | The consent page, in the browser: `response_type=code`, `client_id`, `redirect_uri`, `code_challenge` with `code_challenge_method=S256`, `state`, `scope`, `resource` |
| `POST /oauth/token` | Form-encoded. `grant_type=authorization_code` with `code`, `code_verifier`, `client_id`, `redirect_uri`; or `grant_type=refresh_token` with `refresh_token`, `client_id` (and a narrower `scope`, if wanted). Optional `resource`. Answers `access_token`, `token_type`, `expires_in` (3600), `refresh_token` and `scope`, with `Cache-Control: no-store` |
| `POST /oauth/revoke` | RFC 7009: `token`, `client_id`. A refresh token revokes everything issued since its code; an access token, itself. Always 200 |

- **Client ID metadata documents** (D38). A client may use the https address of its metadata document as its `client_id`, and skip registering; the server's metadata says `client_id_metadata_document_supported`. a4a reads the document at the first authorization, and again once its Cache-Control (five minutes to a day) has run out. The address is https with a path, no credentials, fragment or dot segments, and resolves to a public address; no redirect is followed; the document is JSON of 5 KB at most, its `client_id` is its own address, and it is a public client's (`token_endpoint_auth_method` none, no secret). The consent page names the document's host.
- **Stepping up** (D38). An app allowed only to read that calls a tool that changes something gets 403 and `WWW-Authenticate: Bearer error="insufficient_scope", scope="read write", resource_metadata=…`: it asks its person again, for writing. A viewer's app, whose person can't allow writing, gets the tool's own refusal.
- **Scopes.** `read`, and `write`, which brings `read` with it. Words a4a doesn't know (`openid`, `offline_access`) are left out, not refused, and the token's `scope` says what was given. Never `admin`.
- **The consent page** shows who asks (the name the app gave itself, said to be its own), where it sends the person back, what it may do, and where: every project, or the ones chosen. A person whose role only reads can't allow changes. Allowed once, an app asking for no more carries on without asking, for 90 days from its last use.
- **Errors** are OAuth's: `{ "error", "error_description" }`.
  - On the token endpoint: `invalid_request`, `invalid_client` (401), `invalid_grant`, `unauthorized_client`, `unsupported_grant_type`, `invalid_scope`, `invalid_target`.
  - Sent back to the app: `access_denied`, `invalid_request`, `unsupported_response_type`, `invalid_target`, with its `state` and `iss`.
  - An unknown app, or a redirect it didn't register, is shown on a4a's page and sent nowhere.
- **Lifetimes.** A code lasts two minutes and works once. An access token lasts an hour. A refresh token lasts 30 days and is replaced at each use. A code or refresh token used twice revokes every token since its code.
- **Behind the consent page** (REST, signed in, a4a's own page only): `GET /api/v1/oauth/authorize` checks a request, and `POST /api/v1/oauth/authorize` records the person's decision and says where the browser goes. `GET /api/v1/me/oauth-grants` lists the apps a person allowed; `DELETE /api/v1/me/oauth-grants/{id}` revokes one, and every token it holds, at once.

## 6. Events and webhooks

An agent or integration can react to changes instead of polling.

**Event types**

- `issue.created`, `issue.updated` (with the list of field changes), `issue.deleted`
- `comment.created`, `comment.updated`, `comment.deleted`

What notifications need is in `data`, as logins: `assigned` (new assignees) and `mentions` (people newly mentioned who can see the project) on `issue.created`, `issue.updated`, `comment.created` and `comment.updated`; `watchers` on `issue.deleted`, since they go with the issue. An issue made from a Teams or Slack message (D60) has `data.chat` on its `issue.created`: `platform`, `workspace`, `channel`, `url`, `author` and `sentAt`, and none of the message beyond what the issue holds; its history says "via Slack" or "via Teams" (channel `chat`). A change a workflow rule made carries `data.automation`: the rule's id and name, and how many rules deep in a chain it is.

An event's `actor.isBot` says an agent's account acted as itself (a4a's own, such as triage, or an agent of its own with a token issued to it). A person's undo of an agent's change is `issue.updated` (or `link.created`, `link.deleted`) with `data.undoes`: the event it undoes (D34). A change a person made in a view carries `data.view` (`list`, `timeline` …), and its undo, theirs alone, is the same events with `data.undoes`, one for each issue of its group. Rules skip an undo's events.

Every consumer sees only the events of projects it can see: `GET /events` and `GET /events/stream` filter by the caller's access, and leave out a link whose other end it can't see, and changes to private fields kept from it (D50). Webhooks (made by administrators) get every event, without what's limited to some people (D37) or private (D50).

**Payload**

```json
{ "id": 1042, "type": "issue.updated", "occurredAt": "2026-11-15T10:12:00Z",
  "actor": { "login": "anna", "channel": "mcp", "token": "claude-code", "isBot": false },
  "project": "BACK", "issue": { "id": "BACK-12", "summary": "…", "resolved": false, "state": "In Progress" },
  "changes": [ { "field": "State", "from": "Open", "to": "In Progress" } ], "data": {} }
```

A change to a multi-value field or to the tags joins its values in `from` and `to` with ", ", and lists each in `fromList` and `toList` where a side holds several (`{ "field": "Tags", "from": "ui", "to": "ui, perf", "toList": ["ui", "perf"] }`), for a page to join in its reader's language (D49).

**Delivery**

- **Webhooks:** filtered by event type and project, signed with `X-A4A-Signature: sha256=<HMAC of body>`, beside `X-A4A-Event`, `X-A4A-Event-Id` and `X-A4A-Delivery`. Tried up to 3 times, again after 1 and then 4 seconds (a 4xx other than 408 or 429 isn't tried again), every attempt logged.
- **`GET /events/stream`:** the same payloads over SSE, in id order, from whichever instance serves it.
  - Each frame's `id` is the event id. On reconnect, send it back as `Last-Event-ID` (browsers do this by themselves) or as `?after=`, and the stream first replays what you missed, then goes on live, without repeats.
  - More than 1000 missed events get a `resync` event instead, whose `id` is where the stream goes on from: re-read what you show, or page through `GET /events?after=`.
  - `project` and `types` filter the replay too.
- **`GET /events?after=<id>`:** a durable feed to catch up after downtime.

## 7. AI endpoints

These run on Claude (`claude-opus-5-5`) when `ANTHROPIC_API_KEY` is set, or on DeepSeek, Qwen or another service that speaks Anthropic's Messages API, chosen with `AI_PROVIDER` (see the README). `GET /ai/status` says who serves the model, which model, and why the AI is off when it is. While it's off (without a key, say) they return `503 ai_disabled`, and the non-AI parts keep working (lexical similar-issue search included).

Writing and reading help counts against `AI_WRITING_MAX_PER_HOUR` (100) per person, on every channel: past it, `429 ai_writing_limit` says how many minutes to wait. What's sent is capped by action (12,000 characters to fix or rewrite, 40,000 to summarise, 2,000 for a line to draft from), past which `400 ai_text_too_long` says to select less. Only what the caller may see is sent to the model, and nothing is saved but a summary someone posts.

## 7a. Who sees what (D37)

- **Roles** are sets of permissions: read, comment, create, edit, delete, time, costs, boards, manage, and `readPrivate` and `editPrivate` (a project's private fields, D50). `GET /roles` lists them, the built-in viewer, member and manager first; administrators make, change and delete their own (`POST /roles`, `PATCH`/`DELETE /roles/{id}`). Wherever a role is given (`/projects/{key}/members`, `/projects/{key}/groups`), `role` takes a role's id or name. A project's `access.permissions` says what the caller may do in it.
- **Visible to.** `visibleTo: { users: [logins], groups: [names or ids] }` on `POST /issues` and `POST /issues/{id}/comments`, or later with `PUT /issues/{id}/visibility` and `PUT /comments/{id}/visibility` (`visibleTo: null` lifts it). An issue says `limited`, and its detail and its comments say `visibleTo`.
  - Its reporter and assignee (a comment's author), the project's managers and administrators always see it.
  - To anyone else it's missing, in the words of one that doesn't exist: in lookups, search, links, the event feed and stream, notifications, reports, plans and MCP. Webhooks don't carry it.
  - `add_comment` takes `visibleTo` too.
- **Private fields** (D50). `private: true` on `PUT /projects/{key}/fields/{fieldId}` (its managers; State and the assignee field can't be). Someone whose role lacks `readPrivate` there gets the issue without the field, everywhere: issue reads and lists, `get_project`, `get_issue`, search (an unknown field, or no value where it's public elsewhere), sorting and counts, reports, plans, history, the event feed and stream, notifications, and the AI's prompts. Its changes are taken out of events, and a change to nothing else isn't there. Setting it without `readPrivate` is a field the project lacks (400 `issues.noSuchField`, or a command's problem); with it but without `editPrivate`, 403. An issue's field says `private: true` to someone who sees it. Chat channels, webhooks and triage never get one.
- **Guests**: see Authentication above. An administrator sets `guestAccess` on `PATCH /projects/{key}`, on an open project only.
- **Guests beyond issues** (D64). Without credentials, in the projects open to guests:
  - `GET /boards`, `GET /boards/{id}` and `GET /boards/{id}/view`: the cards a guest may see, in the board's order; a board across projects names and counts only the guest-open ones. Not the backlog, velocity or a sprint's plan. A board's `query` and `backlogQuery` are null to anyone who doesn't see every project on it when they name something that reader can't see, and such a board's view is 400 `boards.queryNamesUnseen`, without the query's words.
  - Every `GET /reports/…` and its `.csv` but the time report, counting only the issues a guest sees.
  - `GET /projects/{key}/schedule`, without a baseline (one asked for is 404, as a missing one), with `away` empty and no warning that someone is away. Money takes the costs permission, for anyone: without it a task's `plannedCost` and `actualCost`, a baseline's and a variance's `cost`, and `calendar.budget` (and a project's `settings.plan.budget`, unless you manage it) are null. The load, costs, baselines, what-if and levelling stay closed.
  - `GET /whiteboards`, `GET /whiteboards/{id}` (with `viewers` empty), `GET /whiteboards/{id}/cards` and `GET /whiteboards/{id}/stream`, which sends no `viewers` and doesn't count a guest among them. Presence is refused. A guest holds four open streams per address (four hundred guests' in all, per instance); past that, 429 `whiteboards.guestStreams`.
  - Every write is 401 `access.signInFirst`; MCP is unchanged, since it needs a sign-in.

## 7b. Apps (D48)

An app is a zip with `manifest.json`: its name, title, version, what it asks for (`permissions`: `read` and `write` of `issues`, `comments`, `articles`, `fields`, `time`), and what it adds, each part saying what it `uses`:

{ "name": "time-by-person", "title": "Time by person", "version": "1.0.0",
  "permissions": { "read": ["issues", "time"] },
  "widgets": [{ "name": "time", "title": "Time by person", "at": "issue-panel", "entry": "widgets/time.html", "uses": {} }],
  "handlers": [{ "name": "by-person", "file": "handlers/by-person.js", "uses": { "read": ["issues", "time"] } }] }

Places a widget goes (`at`): `issue-panel`, `issue-below-summary`, `project-settings`, `main-menu`, `dashboard`, `article-panel`. A rule is `{ "name", "file", "kind": "change" | "schedule", "on": "created" | "updated" | "commented", "field", "query", "every": "hour" | "day" | "weekday", "at": "HH:MM", "uses" }`. A setting is `{ "name", "title", "type": "text" | "number" | "boolean" | "choice" | "secret", "scope": "app" | "project", "default", "choices", "description", "required" }`.

## 8. Security model for agents

- **Tokens.**
  - Random, prefixed `a4a_`, and shown once; only a SHA-256 hash is stored.
  - Each has a name, scopes, an optional expiry and a last-used time, and can be revoked at any time.
  - A read-only token is the safest way to let an agent explore.
- **Apps that sign in (OAuth).**
  - The person chooses what each app may do and where, on a4a's own page, and revokes it under Agents and tokens.
  - Its tokens are hashed, short-lived, work at `/mcp` alone, and never carry `admin`.
  - The activity names the app.
- **Prompt injection.** Issue text is untrusted, since anyone who can file an issue can write instructions into it.
  - The assistant's system prompt, and the MCP server's instructions to agents, treat tool output as data.
  - In the in-app assistant, writes wait for the person's approval, unless they let it act.
  - MCP write tools are annotated so clients prompt before running them.
- **Blast radius.**
  - No deleting issues, articles, files or whiteboards over MCP.
  - Bulk commands are capped at 50 issues, with `dry_run` available.
  - Result sizes are capped.
  - A per-token rate limit applies (`MCP_RATE_LIMIT`, 600 requests a minute on each instance).
- **Audit.** Every change records actor, channel and token, so you can always answer *"which agent did this?"*.
- **Notifications.** An agent sees its person's inbox (`list_notifications`, with `read`), and changes it only with `write`. What's in it was written by people, and is information, not instructions.

## 8a. The help desk's public surface

People outside the team reach a project's help desk without signing in, so these routes are built to tell them nothing beyond their one request:

- **The form** (`/help/<KEY>`) answers the same 404 whether the project doesn't exist or its help desk is closed. Posting needs an `Origin` of this server, and a form token: signed, naming the project and a nonce in a `SameSite=Strict` cookie, and good for 6 hours. A field hidden from people (`website`) catches bots: filled in, the answer is the usual one and nothing is filed. Limits: 5 requests per address in 15 minutes, 3 per email an hour, 120 per help desk an hour; bodies over 48 KB are refused, and each field has its own limit.
- **A request is filed as an issue** reported by the `helpdesk` agent for the requester, who isn't a user: their email and name are kept apart, as a requester, never among people to assign or mention. What they write mentions nobody.
- **The tracking token** is 256 random bits, kept only as a SHA-256 hash. Each email to the requester carries a fresh one, minted as it's sent, so none waits in plain text; every one stays good for the request until it's deleted. In a link it sits in the fragment (`/request#hdt_…`), so it never reaches a server's logs or another site's `Referer`; to the API it travels in a header. Any wrong token, malformed or not, gets the same 404.
- **The request's page** shows its summary, its state, what the requester wrote and the public replies, never an internal comment, a field, an issue id or anyone's email but their own. The requester's replies are public comments that tell the issue's watchers.
- **A proof of work, when the desk asks for one** (`settings.helpdesk.captcha`). The form comes with a challenge the server signed: find the number up to `maxnumber` whose SHA-256 of `salt` and number is `challenge`. The browser finds it with WebCrypto, in a worker of the site's own, and the request carries it as `captcha`; the server checks it, for that desk and while it's good (30 minutes), and takes it once. Nothing to solve by hand and nothing from another site: it makes each request cost a bot a moment, not a person. A wrong or spent answer is `400 captcha_failed`, an old one `400 captcha_expired`; the page fetches a new challenge either way.
- **By email** (D30). A desk with an address takes requests and answers by mail, posted by its mail provider to `POST /mail/inbound/<KEY>` or read from the server's shared mailbox. The provider authenticates with the desk's secret as HTTP Basic's password; a desk that doesn't exist, takes no mail, or has another secret answers the same 401, and such posts are limited per address. Each message counts once (by Message-ID). A reply is taken only from the requester's own address, to a reply address whose token is the request's, or answering an email a4a sent them (whose Message-ID is random). Auto-replies, bounces, list mail and a4a's own are set aside; nobody is ever told of what was set aside or refused, so a forged sender gets no mail. Limits: 5 new requests per sender, 30 replies per request and 300 messages per desk, each an hour; 25 MB a message (`HELPDESK_MAIL_MAX_MB`).
- **The portal's own sign-in** (D63) is public too: asking for a link to set a password answers alike for any address; a password sign-in says "Wrong email or password" alike for an unknown address, one without a password and a wrong one, and takes as long; a desk's sign-in page names only its own providers.
- **What's missing:** checking that the email is the requester's before anything is filed (anyone can file in another's name, by the form or by forging a sender, and the confirmation then goes to that address, so the per-email limits cap it; a desk's mail is refused when its own server says it failed DMARC); and attachments on the form (by email they come). The limits are shared by every instance; behind a proxy, set `TRUST_PROXY` so they count the client's address rather than the proxy's.

## 8b. The help desk in depth (D45)

- **SLA policies:** `GET|POST /projects/{key}/sla-policies`, `PUT|DELETE /projects/{key}/sla-policies/{id}`, `PUT /projects/{key}/sla-policies-order`. Targets in business minutes; the desk's working hours, waiting states and resume state are `settings.helpdesk.businessHours`, `waitingStates` and `resumeState` on `PATCH /projects/{key}` (its `organizations` are customer groups now, D56: a change that gives any is refused with a 400 that says so). `GET /issues/{id}/request` has `sla`: its policy, status and each target's clock. `GET /projects/{key}/sla-report?from&to&tz`: met and breached by policy, per week, and over the period by customer group (`groups`).
- **Search:** `sla: on track | at risk | paused | breached | met | overdue | due | missed`, `first response: …`, `resolution: …` (due, at risk, paused, overdue, met, missed, breached), `first response due: <date>`, `resolution due: <date>`. The "SLA status" field reads as any enum field.
- **Events:** `sla.warning` and `sla.breached` (`data.target`, `policy`, `dueAt`, `targetMinutes`), as webhooks and in history.
- **A desk's own mailbox:** `GET|PUT /projects/{key}/helpdesk/mailbox` (`imapUrl`, an administrator's to set, sealed; `fromName`, the managers').
- **Customer groups (D56):** `GET|POST /projects/{key}/customer-groups`, `GET|PUT|DELETE /projects/{key}/customer-groups/{id}` (a name, `domains`, `sharing`: none, read or comment, `businessHours`, `agents` as logins in order; the desk's managers change them, its people read them), `GET|POST /projects/{key}/customer-groups/{id}/members`, `DELETE /projects/{key}/customer-groups/{id}/members/{requester}` (requesters added by hand, by email). A group says how many people its new requests would copy (`people`) and how many stopped its emails (`stops`); `GET /projects/{key}/customer-groups/{id}/copy-stops` lists who, for anyone who reads the desk. A domain names one group at a desk, and a requester is in one: 409 names the group that has them. `PATCH /issues/{id}/request` (`group` by id or name, or null; `private`; `expectedVersion`) changes a request's group or keeps it from the group, with the edit permission, in its history as `Customer group` and `Private` changes on `issue.updated`. `GET /issues/{id}/request` says its `group` and whether it's `private`. Search: `customer: <name>`, `has: customer`. A member's reply is `comment.created` with `data.requester` (their name) and `data.colleague: true`; the desk's assignment to an agent is `issue.updated` by the `helpdesk` agent through `automation`, with `data.customerGroup`.
- **The portal** (no team sign-in; its own cookie): `POST /portal/sign-in` (an email; 202 alike for any address; the link is in the address's language, else the asking page's `x-a4a-locale`, and changes nothing of the address), `POST /portal/sign-in/redeem` (a link's token, once), `POST /portal/sign-out`, `GET|PATCH /portal/me` (`name`, and `locale`: the language of the portal and every email to them, null for their browser's, D63's revisit), `GET /portal/desks`, `GET /portal/requests`, `GET /portal/requests/{id}`, `PATCH /portal/requests/{id}` (`private`: their own request, kept from their group or shared again), `POST /portal/requests/{id}/replies` (their own, or their group's where it shares to comment), `POST /portal/requests` (`private` too). `GET /portal/me` lists the groups that share with them (`groups`, each with its `id` and whether its new requests copy them, `copies`), how this session was opened (`signedInWith`), and the desks with requests of theirs it doesn't open, with how each signs them in (`elsewhere`). `PATCH /portal/me/groups/{id}` (`copies`) is their switch: off stops the group's emails as its link does, on copies them on its later requests; a group not theirs is 404 `portal.noGroupHere`, alike with none. Not an MCP tool: a requester's own email settings aren't work on issues (D8). The team: `POST /issues/{id}/request/invite` (a sign-in link, or a link to set a password, as the desk takes).
- **The portal's own sign-in (D63):** a desk's `settings.helpdesk.signIn` (`link`, `password`, `providers`: the ids of identity providers for requesters); a customer group's `provider` ties its people to one of them at that desk. `GET /portal/sign-in-methods?desk=` says a desk's ways (or, without one, the ways some desk takes, naming no provider) and carries a proof-of-work `captcha` when a desk that takes passwords asks for one. Passwords: `POST /portal/password/link` (202 alike for any address; limited with sign-in links), `POST /portal/password/set` (the link's token, once, 20 minutes; ends their sessions, starts one), `POST /portal/password/sign-in` (10 wrong per email in 15 minutes lock it, `429 portal.tooManyTries`), `PUT /portal/me/password` (the current one first). Single sign-on: `GET /portal/sso/{id}/start?desk=` and `GET /portal/sso/callback`, for browsers; failures come back as `/portal?sso=cancelled|expired|failed|unverified|domain|refused`. Providers: `GET /portal-providers` (administrators and desks' managers), `POST`, `PATCH`, `DELETE` (administrators; refused while a desk offers one). Not an MCP tool: sign-in is security configuration a person chooses. A requester's language (D63's revisit): each sign-in takes the one they chose on the page before it, `locale` in the bodies of `/portal/sign-in/redeem`, `/portal/password/sign-in`, `/portal/password/set` and `/portal/passkey`, and on `GET /portal/sso/{id}/start`, which keeps it in the sign-in's state; it becomes theirs only if they have none, and a language a4a doesn't speak is a 400. `GET /issues/{id}/request` says the requester's language (`requester.language`: `{ locale, chosen }`, chosen on the portal or their browser's; null when a4a knows neither). No tool sets it: it's the requester's own.
- **The portal's passkeys (D69):** a desk's `settings.helpdesk.signIn.passkey` (beside another way, never alone: 400 `portalSignIn.passkeyNotAlone`; left out, the desk keeps what it had); `GET /portal/sign-in-methods` says `passkey`, and `PortalMe.elsewhere` a desk's. Signing in: `POST /portal/passkey/options` (`{ desk? }`; sets the `a4a_portal_pk` ticket cookie, for `/api/v1/portal/passkey` alone) and `POST /portal/passkey` (`{ response, desk? }`; sets the portal's cookie; `PortalMe.signedInWith.method` is `passkey`). A requester's own: `GET /portal/me/passkeys` (`on`, `off`: address, instance or desks, `confirmedUntil`, `confirmWith`: `passkey`, `link`), `POST /portal/me/passkeys/options` and `POST /portal/me/passkeys` (`{ response, name? }`), `PATCH /portal/me/passkeys/{id}` (`name`), `DELETE /portal/me/passkeys/{id}`; confirming with a passkey: `POST /portal/me/confirm/passkey/options`, `POST /portal/me/confirm/passkey`. Each try counts in the sign-in throttle, per address and per passkey; challenges are 30 a minute per address. Mails' links: `GET /portal/not-me?token=` says what changed, `POST` signs the requester out of the portal everywhere and stops the passkey. The team: `DELETE /issues/{id}/request/passkeys` (an administrator, or a manager of the request's desk: 403 `portalPasskeys.forManagers` otherwise) answers `{ removed }`.
- **Kinds of change:** `GET|PUT /me/notification-kinds` (`watching`, `defaults`: each kind's `{ inbox, email }`), `PUT /subscriptions/{id}/kinds` (`null` follows the defaults).
- **Replies by email:** comments made by answering a notification email have the `email` channel.

## 8c. CCs on help desk requests (D57)

- **Who:** `GET|POST /issues/{id}/request/ccs` (`email`, and a `name` if known), `DELETE /issues/{id}/request/ccs?email=`; `GET /issues/{id}/request` lists them as `ccs`. The Cc of the requester's own email copies people too, a new request's or a reply's; never mail no person wrote, nor anyone else's mail. On the portal, `POST /portal/requests/{id}/ccs` (its requester alone); `PortalRequest.copied` marks a request the signed-in person is copied on, which they see and reply on; `PortalRequestDetail.ccs` is the list, for its requester (null for anyone else).
- **What they get:** each public reply and change of state the requester gets (not the acknowledgement, not their own or anyone else's words outside the team, never anything internal), each in an email of their own, in their language when the address is a requester's a4a knows, else the desk's (D63's revisit): a reply address whose token answers for their address alone, a link to the request on the portal (never the requester's tracking link), and an unsubscribe link (`kind: cc`) that takes them off.
- **A customer group's copies (D56):** where a group shares its requests (`read` or `comment`) and one isn't kept private, its people are copied as it's filed: `RequestCc.via` is `group`, `group` its name, and `hears` whether the group still shares it with them, checked as each email goes (a copy that doesn't hear gets nothing, and the portal doesn't list it). Their emails say it's because of the group; only where it shares to `comment` do they carry a reply address. Their unsubscribe link (`kind: group`, its `group` naming the group and desk) takes them off the group's open requests, `request.cc_removed` with `via: group`, `group` and `where` (`link` or `portal`), and its later ones don't copy them.
- **Their answers:** to their reply address, answering an email a4a sent them, or answering the request's first message, from their own address while they're copied: a public comment by the `helpdesk` agent as their requester account (`Comment.requester.as` is `copied`; a colleague of the requester's customer group writes as `colleague`, D56), cut from what it quotes. Anything else to their reply address is refused, and nobody is told. On the requester's tracking page and the portal their messages are `from: cc`, a colleague's `from: colleague`.
- **The SLA:** their answers are the customer's side: they end a wait on the customer, as the requester's do, and never count as the team's first response.

## 8d. CCs in depth (D67)

- **Taking off:** `DELETE /portal/requests/{id}/ccs?email=`, the request's requester alone, signed in to the portal, from the portal's own page: anyone copied, whoever copied them. The row stays, so an email's Cc doesn't copy them again; the team or the requester may. A colleague or someone copied gets 403 `portal.onlyTheRequesterChangesCopies`.
- **A desk's cap:** `settings.helpdesk.ccsMax`, 1 to 50, default 20; each request says it (`HelpdeskRequest.ccsMax`, `PortalRequestDetail.ccsMax`). Past it a copy is refused with 409 `requestCcs.full` and `values.max`, on every door; lowering it takes no one off.
- **Trust:** an email is trusted when its sender's domain passed DMARC at a server named in `HELPDESK_TRUSTED_AUTHSERV_IDS`, read from the topmost `Authentication-Results` header such a server wrote (RFC 8601); `GET /projects/{key}/helpdesk/mail` lists them as `trustedServers`. Words written on the portal, signed in, are trusted; the tracking page's aren't.
- **Held CCs:** a new request by email from a sender a4a can't trust has its Cc held (`HelpdeskRequest.held`, `PortalRequestDetail.held` for its requester), told nothing, unless the desk's `settings.helpdesk.ccsConfirm` is off. The acknowledgement carries a link, `/portal#hdc_…`, good once for 3 days: `GET /portal/cc-confirmation` says whom it holds, `POST /portal/cc-confirmation` with `{ copy: [emails] }` copies those and drops the rest, the token in the `x-cc-confirmation` header either way; a stale, used or unknown one is 401 `requestCcs.confirmLinkExpired`. Signed in: `POST /portal/requests/{id}/held-ccs` with `{ email, copy }`. Holds are forgotten after 30 days.
- **Hearing each other:** with `settings.helpdesk.ccsRelay` on, a trusted public comment from outside the team (`comment.created` with `data.relay: true`) is emailed to everyone else on the request: its requester, those copied, and colleagues of its customer group who answered it. Each email comes from the desk, has a reply address of its own, names who wrote, quotes nothing older, and carries no file, only how many came (`data.files`). At most 20 a request and 10 a sender each hour; the desk's log (`GET /projects/{key}/helpdesk/mail/log`) says why words weren't relayed, with `via: page` or `portal` for words written there. A colleague stops hearing them by the email's unsubscribe link (`kind: relay`).

## 9. Open questions

These are the decisions worth thinking through together. v1 ships with the defaults in brackets.

1. **Deletes over MCP.** Should agents ever delete issues? [No. Agents resolve instead, for example `State Obsolete`.]
2. **Agents as teammates** (later). Bot users that pick up the issues assigned to them and report back. Partly done (D34): an administrator adds an agent of its own and issues its tokens; it is assigned issues as a person is, acts as itself, and finds its work with `for: me #Unresolved`. Still open: telling an agent of its work (a notification, or a webhook that wakes it), so it needn't search for it.
3. **OAuth 2.1 for remote MCP.** Done (D28): a4a is the authorization server for its own `/mcp`, so claude.ai custom connectors and other MCP clients sign in by themselves (5.6). API tokens stay, for clients that don't.
4. **Per-project token restrictions.** Done: a token can be limited to projects, e.g. one that only touches `BACK`.
5. **VCS integration.** Done (D26, D33): GitHub, GitLab, Bitbucket, Gitea and Forgejo integrations link commits and pull requests, and `BACK-12 #Fixed` applies as the commit's author, known by any email they confirmed, or by their login at the provider, which an administrator records or they connect themselves (D46, D54). A login reaches commits under a provider's no-reply address, except at GitLab, which names no account for a commit.
6. **Partial responses** (later). A YouTrack-style `?fields=id,summary,fields(State)` selector for heavy integrations.
7. **Agent-specific limits.** Should MCP writes be rate-limited separately from humans, or require a second human approval for bulk changes over N issues? [MCP has its own limit per token, `MCP_RATE_LIMIT` (600 requests a minute on each instance), for reads and writes alike; a command takes 50 issues at most, and nothing asks a second person.]
8. **The help desk by email.** Done (D30): mail to a desk's address files requests, and answers to its emails become the requester's public comments, from a provider's webhook or the shared mailbox. A desk can read a mailbox of its own (D45). People copied on a request answer by email too (D57), and so do colleagues in the requester's customer group, where it shares to comment (D56).
9. **Per-person time zones.** Done (D31): a person's zone, on their profile, is where their searches read "today", when their digest comes and the zone of their email's times. Rules and agents with no person read the server's.
